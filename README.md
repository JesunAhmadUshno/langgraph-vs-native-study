# LangGraph versus Native: a pre-registered paired study

**Question.** With the decision policy, tasks, tools and budgets held
identical, what does the LangGraph orchestration layer change against a
hand-written loop on task success, consistency, cost, and exactly-once
recovery after a process kill?

**Headline.** After a process kill both arms kept every side effect exactly once in 48 of 48 runs (exact 95% interval [0.926, 1.000] each), so on recovery the orchestrator added nothing measurable; what recovery cost differed, with LangGraph re-running one already-finished step in all 24 step-boundary kills against none for the native loop, and LangGraph's median wall time was 0.299 of the native loop's (paired bootstrap 95% interval [0.274, 0.342], implementation-sensitive).

**Field.** ML and AI research. **Job family.** AI engineering (agent
systems).

**Verdict.** Functional. SPEC.md and HYPOTHESES.md were committed in
c484e54 before any harness, arm or analysis code (tag proposal-v1), the
registered suite has run end to end (192 main runs and 96 killed and
resumed fault runs, results/), tests pass in CI on Python 3.11 and 3.12,
and CI regenerates every reported number from the raw files. Evaluated
waits for the field profile: no ablation has been run, H4 is Not yet
measured, the success test is degenerate by design (a scripted policy,
not a model), and there is one suite pass on one machine.

Live dashboard: https://jesunahmadushno.github.io/langgraph-vs-native-study/

## Reproduce

```text
python -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q          # unit, smoke and layout tests
.venv/bin/python -m study.analyze      # regenerates RESULTS.md and results/ from the raw files
git diff --exit-code RESULTS.md results/
.venv/bin/python -m study.run_suite    # reruns the study: 192 main runs, 96 fault runs
```

The last command reruns the whole registered suite (CPU only, a few
minutes) and overwrites the raw files; under the stop rules in
HYPOTHESES.md a rerun is logged in DECISIONS.md and reported whole.
Versions are pinned in requirements-lock.txt and printed into
results/env.json by the suite. The dashboard in site/ reads the
committed result files at build time; `cd site && npm ci && npm run
build` first runs a known-answer check that reproduces every in-browser
computation against them.

## Design in one paragraph

Two arms run the same 12 tasks with the same scripted decision policy,
the same tools, the same step executor, the same budgets, paired by
seed. One arm sequences the work with LangGraph 1.2.20 and its SQLite
checkpointer. The other uses a hand-written loop with its own SQLite
event log. Hypotheses were committed before any experiment code
(HYPOTHESES.md).

## Layout

Files named in the locked SPEC.md and HYPOTHESES.md keep their names;
the second column gives the role each plays in the portfolio standard.

| Path | Role | What it holds |
| --- | --- | --- |
| SPEC.md | proposal | Locked question, design, fault suite, metrics and controls (tag proposal-v1); a test fails if one byte changes |
| HYPOTHESES.md | proposal | Locked H1 to H4 with pass lines, stop rules and predictions (tag proposal-v1); same test |
| METHODS.md | report (method) | Formulas, fault injection, measurement limits, threats to validity |
| REPORT.md | report | Background, hypotheses scored, misses, review notes, audits, limitations, the Deep pass |
| RESULTS.md | results | Every number, generated by study.analyze from the raw files |
| results/ | evidence and results | raw_main.json, raw_fault.json, env.json, fixtures.json (pinned by SHA256SUMS); summary.json and readme_table.md generated |
| DECISIONS.md | decisions | D1 to D10, each dated by its commit |
| RESEARCH.md | report (prior work) | The evidence table with its verification statuses |
| study/ | code | Both arms, the shared core, the suite runner and the analysis |
| tests/ | tests | Tools, policy, tasks, scoring, analysis, reproduction, arm smoke tests, the layout and lock test |
| site/ | dashboard | The live dashboard, built from results/, study/tasks.py and REPORT.md |
| CHANGELOG.md, CITATION.cff, SECURITY.md, LICENSE | release | Change history, citation, how to report a vulnerability, Apache-2.0 |

There is no experiments/ folder: the raw evidence predates the standard
and lives in results/ beside the generated files, pinned by
results/SHA256SUMS. There is no docs/decisions/ folder: DECISIONS.md,
named by the locked HYPOTHESES.md, holds the decision records.

Code in study/:

- study/tasks.py: the 12 fixtures and their intended side effects.
- study/policy.py: the scripted policy, identical in both arms.
- study/tools.py: lookup, append_record (a local ledger file),
  was_applied. The ledger tool does not deduplicate; exactly-once is
  the orchestrator's problem.
- study/executor.py: the shared per-step executor and retry budget.
- study/arm_langgraph.py: the graph arm (one node per step, SQLite
  checkpointer, idempotent node pattern).
- study/arm_native.py: the loop arm (state committed per step,
  write-ahead intent log for effects).
- study/run_suite.py: main suite in process, fault suite as killed
  and resumed subprocess pairs.
- study/analyze.py: every number in RESULTS.md, computed from the raw
  files.
